# CTGents 功能演化边界

> 状态：现役架构约束
> 目标：停止横向堆功能，把已有能力收口成可验证、可观测、可退化的完整闭环。

## 一、产品边界

CTGents 是单用户、单主 Agent 的编程与科研工作台。核心价值不是“拥有最多工具”，而是：

1. 在一个可信主循环中完成真实工作；
2. 长任务能计划、推进、验证、暂停和恢复；
3. 有价值的经验能留下出处，在后续任务中被正确复用；
4. 失败能被发现、定位并转化成回归保护。

核心源码与个人积累必须物理分离：代码、测试、文档和内置资源属于可发布核心；
memory、knowledge、sessions、tasks、stats 属于 `CTG_WORKSPACE_DIR` 指向的个人项目。
不得再以“同仓库但 `.gitignore`”代替所有权边界。

以下方向暂时冻结，除非真实使用数据证明现有边界无法满足需求：

- 新 LLM provider 和自动多模型路由；
- 新 UI 形态；
- 新 Agent 拓扑或多 Agent 平台化；
- 通用插件市场、自安装代码和自动改写自身；
- 新的记忆类别、新的工具大类；
- 只增加展示、不参与决策或验证的新指标。

允许的演化只有五类：**补闭环、减重复、强验证、提可观测性、删除失效机制**。

## 二、模块职责边界

### 1. 交互层：`tui.py` / `ui.py` / 行式 REPL

只负责输入适配、事件转发和结果渲染。

- 不拥有任务策略；
- 不直接修改记忆、psyche、skill 或工具注册状态；
- 不实现另一套对话循环；
- 所有入口必须汇入 `main.run_agent_turn`。

### 2. 生命周期编排层：`main.py`

只拥有“一轮工作”的生命周期：

`准备上下文 → 驱动对话 → 必要时续跑任务 → 保存会话 → 收尾`

- 不下沉工具实现；
- 不实现领域判断；
- 不新增与 `run_agent_turn` 平行的主干；
- 跨子系统接线必须在这里可见，或由这里显式调用的生命周期对象承载。

### 3. 推理执行层：`llm.py` / `cache_context.py`

只拥有模型请求、工具循环、上下文预算、重试和中断恢复。

- 不拥有任务事实；
- 不直接决定哪些经验值得永久记忆；
- 不写业务产物；
- 不把 UI、研究领域或具体工具规则硬编码进循环。

`cache_context.py` 只维护消息结构与 API 发送视图，不承担业务记忆。

### 4. 能力层：`tools/`

工具是原子能力，不是隐式工作流。

每个工具必须：

- 有单一清晰副作用；
- 明确安全等级、失败语义和幂等性；
- 返回可供上层验证的结构化证据；
- 不偷偷触发另一个长流程；
- 不拥有跨会话策略。

跨三个以上工具的固定流程应成为 skill；需要持续状态、重规划和停止条件的流程应成为 task，
不能继续堆进单个工具。

### 5. 任务层：`tasks.py` / `task_loop.py`

只拥有长期目标的执行状态：

`目标 → 步骤 → 当前动作 → 验收条件 → 阻塞/完成 → 归档`

任务清单不是完成证据。`[x]` 和 `task_done` 只能表达 Agent 的控制意图；真正完成必须由任务验收条件
和终止验证器共同确认。

### 6. 可信层：`guard.py` / `tool_guard.py` / `verifier.py` / `delegate_gate.py`

分成两类，不混用：

- 动作前门禁：权限、路径、危险命令、调用边界；
- 动作后验证：产物存在、行为结果、测试、引用和任务验收。

可信层必须是本地、确定性、快速、失败可解释的。提示词提醒、Agent 自评和 LLM 打分不能成为硬门禁。

### 7. 认知资产层

五种载体严格分工：

| 载体 | 唯一职责 | 不应承载 |
|---|---|---|
| session | 发生过什么，作为可追溯事件记录 | 永久规则 |
| memory | 已验证、跨任务仍有价值的用户偏好或经验 | 大段资料、临时进度 |
| knowledge | 外部事实、论文和研究材料 | 用户偏好、执行策略 |
| psyche | 稳定的判断原则 | 工具步骤、项目事实 |
| skill | 可重复的工作流程 | 长期人格、任务状态 |

同一信息只能有一个权威载体；其他载体只保存引用，不复制全文。

### 8. 可观测与演化层：`tracker.py` / `diagnostics.py` / `gaps.py` / `organs.py`

只负责：

`记录事实 → 发现异常 → 形成候选改进 → 显式批准 → 进入任务 → 验证收益`

监控结果不得直接修改代码、记忆或策略。没有消费者的指标应删除；不能转化成候选改进的异常不算闭环。
候选改进必须记录“接受、拒绝或延期”，修复后必须用相同信号验证是否真的改善。

### 9. 无人期工作层：`heartbeat.py`

只推进明确写入 frontier 的低风险工作：

`读取 frontier → 执行受限工作 → 机械出处闸 → 生成 digest → 主会话消费`

Heartbeat 不自行发明长期目标，不修改核心代码，不绕过主任务优先级，不把“产生了文件”当成“产生了价值”。

## 三、四个必须闭合的系统循环

### 工作闭环

`用户意图 → 任务/直接动作 → 工具执行 → 结果验证 → 明确完成或阻塞`

当前状态：最小任务验收合同、验证回执和结构化停止条件已经落地。剩余缺口是超出
`steps / file / command` 的目标语义验收。

### 学习闭环

`事件 → 有出处的经验候选 → 筛选写入 → 后续召回 → 实际应用 → 效果反馈`

当前状态：资产生命周期和最小使用证据链已经闭合。记忆更新有 revision，替代项退出召回，删除进入
可恢复归档；知识索引严格跟随源文件新增、修改和删除。`recall`/`rag_search` 只为实际返回项记录
`retrieved`，agent 只有显式声明具体用途才能记录 `adopted`，任务机械验收、失败或放弃再写入
`outcome`。已有任务结果的采用可再由 `feedback_asset` 显式标记 `helpful` 或 `misleading`
并说明理由；系统不从 outcome 自动推断价值。审计只基于这些事件报告误导、反复检索未采用和
待价值反馈候选，不自动降权或清理。

### 可靠性闭环

`失败 → 自动检测 → 根因分类 → 修复任务 → 回归测试 → 同类失败率下降`

当前状态：gap 已有稳定 ID、持久化决策状态和原信号机械复核；检测源失败不会误通过，已验证问题复发会重开。
performance gap 会冻结修复前基线，并要求修复后的 3 个有效会话中同类异常零复发；没有工具暴露机会的会话
不计入观察窗口。静态 gap 仍使用即时确定性重扫。

### 自主工作闭环

`明确目标 → frontier/task → 有界执行 → 机械验证 → digest/交还 → 用户确认`

当前状态：Task 与 Heartbeat 保留各自状态所有权，但已共享 work_id、证据哈希、产物版本和交还回执。
Heartbeat 只有出处闸通过且 frontier 真推进才算完成，digest 送达后由用户显式
accept/revise/reject。剩余缺口是主任务与 frontier 同时活跃时的统一调度优先级。

## 四、新功能准入门

任何新功能在编码前必须回答：

1. 它关闭上述哪个闭环中的哪个缺口？
2. 现有模块为什么不能完成，是否只是需要补接线或删重复？
3. 谁拥有它的状态？状态落在哪里？谁有权修改？
4. 成功和失败如何被确定性验证？
5. 如何观测它是否真的被使用、是否产生收益？
6. 失败时如何降级，是否会阻塞主循环？
7. 将来删除它时，哪些数据、入口和文档需要迁移？

答不出第 1、3、4 项，不进入实现。只是“可能有用”或“别的 Agent 有”的功能不进入路线图。

## 五、功能完成定义

一个功能只有同时具备以下内容才算完成：

- 一个明确 owner 模块；
- 输入、输出、副作用和失败语义；
- 唯一状态来源和持久化策略；
- 动作前安全门；
- 动作后成功验证；
- 单元测试和至少一个主循环缝测试；
- 可观测的使用/失败信号；
- 用户可理解的降级或阻塞反馈；
- 对应文档，以及替代旧机制时的删除清单。

只有实现和单元测试的功能状态是 **experimental**；接入主循环但没有验证与观测的是 **integrated**；
完成以上全部条件后才是 **closed-loop**。

## 六、当前收口顺序

### 当前能力状态

| 功能域 | 当前状态 | 成熟化缺口 |
|---|---|---|
| 主对话、重试、中断、上下文管理 | closed-loop | 保持稳定，停止扩面 |
| 原子工具执行与动作前安全门 | closed-loop | 补齐少数工具的结构化证据 |
| 长任务续跑与动态重规划 | closed-loop | 最小验收、验证回执和停止合同已闭合；仍缺目标语义验收 |
| session 保存、摘要与恢复 | closed-loop | 保持单一主干，清理旧叙事 |
| memory 写入与召回 | closed-loop | 生命周期、采用、任务结果和显式价值反馈已闭合；积累真实样本 |
| knowledge/RAG/论文流水线 | closed-loop | 源文件/索引生命周期、采用反馈和产物版本已闭合；观察真实检索质量 |
| psyche/skill 激活与作用域 | integrated | 缺效果指标和退役判据 |
| tracker/diagnostics/gaps | closed-loop | 状态化整改、同信号复核和 performance 跨会话收益窗口已闭合 |
| organs | observational | 除共享工作回执外的旧体征缺少明确消费者，不单独算闭环 |
| heartbeat | integrated | 单跳验收、产物版本和 digest 处置已闭合；缺与主任务统一调度优先级 |

### Phase 0：冻结与清点

- 冻结新增工具、记忆类型、provider、UI 和自主机制；
- `docs/features.md` 旧功能快照已退役删除；现役能力以本表和代码为准，历史变化查 changelog；
- 建立唯一的现役能力表，每项标记 experimental / integrated / closed-loop / retired；
- 修复当前 lint 和测试，使基线全绿。

### Phase 1：先闭合工作闭环

- 给任务增加目标、验收条件、验证命令/证据和停止条件；
- `task_done` 只在验收通过后归档；
- 让 verifier 支持任务声明的验收器，而不是继续增加通用自然语言启发式；
- 把测试提醒从“改了 Python 就 warn”升级为按任务风险选择验证。

任务可声明可调停止边界：

```markdown
## 停止条件

- `budget: 8`
- `stall: 2`
- `deadline: 2026-07-28T18:00:00+08:00`
```

- `budget`：一次自主续跑最多执行 1–100 步；
- `stall`：连续 1–10 步没有推进任务清单时交还用户；
- `deadline`：必须是带时区的 ISO 8601 时间，到期后不再开始新步骤；
- 停止合同每一步重新解析，`update_plan` 修改后下一步生效；
- 重复、未知、越界或无时区规则失败关闭，不带合同的历史任务使用系统默认值；
- 用户中断、`need_user`、`[!]/[r]` 阻塞、验收失败是系统硬停止，任务不能配置关闭。

最小验收合同已采用兼容现有 `current.md` 的 Markdown 格式：

```markdown
## 验收

- `steps`
- `file: docs/report.md`
- `command: py -m pytest tests/test_example.py -q`
- `command: py -m ruff check src/example.py tests/test_example.py`
```

- `steps`：任务正文不得残留未完成或阻塞步骤；
- `file:`：目标必须是项目目录内真实存在的文件；
- `command:`：只允许 pytest、`ruff check` 和 `git diff --check`，不开放任意 shell；
- 已声明 `## 验收` 却没有合法结构化规则时失败关闭；
- 通过后把逐条证据写入 `## 验收结果`，再执行自动归档；
- 没有 `## 验收` 的历史任务继续按旧行为运行。

验证命令已接入持久化回执：

- 正常同步 `run_command` 拿到真实退出码后，为白名单验证命令生成回执；
- 回执绑定规范化命令、工作目录、Python/OS 运行时和完整工作区指纹；
- 指纹覆盖 HEAD、tracked diff 和普通未跟踪文件内容，不用 `git status` 的 `M` 标记冒充内容未变；
- 任务验收优先复用 24 小时内的同状态回执，命中时不重复运行；
- 成功和失败都可成为证据；代码变化后旧回执自动失效，显式重跑可刷新偶发失败；
- 回执保存在被 Git 忽略的 `tasks/verification-receipts.jsonl`，最多保留最近 200 条；
- `run_async` 和同步超时转后台会冻结启动时工作区指纹；
- `poll` 与自动完成通知共享幂等最终化入口，只有一个完成者能写一次回执；
- 后台完成时工作区指纹必须仍与启动一致；失败退出写失败证据，超时被杀或代码变化不写回执。

### Phase 2：闭合可靠性闭环

- gap 候选已采用稳定 ID 和 discovered / accepted / rejected / deferred / fixed / verified 状态；
- `/fix N` 显式接受候选；`/gap` 支持拒绝、延期、重开、标记修复和复核；
- `fixed` 记录工作区指纹，`verify` 强制按原检测源复测；原信号仍在或检测源失败都不能关闭；
- 已验证 gap 再次出现时自动回到 accepted，保留完整历史；
- performance gap 绑定 `tool + anomaly_type`，fixed 时保存修复前基线；
- performance 收益复核要求修复时间之后至少 3 个有效会话且同类异常零复发；无工具调用或样本不足不算证据；
- 通过后继续监测 verified 时间之后的新会话，历史异常不会造成误重开，新复发会自动回到 accepted；
- 台账保存在被 Git 忽略的 `tasks/gap-ledger.json`，扫描缓存绑定完整工作区指纹；
- 删除长期没有消费者的统计和反思产物。

### Phase 3：闭合学习闭环

- memory 更新保留稳定身份、created/revision，冲突替代退出活跃索引，forget 使用可恢复归档；
- knowledge 原文是唯一事实源，索引对新增、修改、删除和空库可靠失效；审计不自动删除原始资料；
- memory/knowledge 使用事件区分“被检索”“被采用”“参与任务结果”和显式价值反馈；
- helpful/misleading 必须有具体理由且指向已有 outcome 的采用，不从任务通过自动推断资产有效；
- 审计报告误导、反复检索未采用和待反馈候选，仍不自动降权、修改或删除；
- memory 仍可按价值补出处、适用范围和最后人工验证时间；
- 对低价值、冲突和长期未验证记忆做显式降权，不恢复全自动 LLM 收割。

### Phase 4：统一自主工作

- 统一 task continuation 与 heartbeat 的目标、风险、验收和交还合同；
- 明确主任务永远高于无人期 frontier；
- digest 被主会话消费后记录接受/拒绝，避免只产生无人确认的资料；
- 只有前三个闭环稳定后，才扩大自主执行范围。

## 七、近期明确不做

- 不因为大文件而进行一次性全面重构；
- 不新增“更聪明”的 LLM 审计器代替确定性验证；
- 不恢复自动用户画像或会话末全量记忆收割；
- 不恢复独立 Dashboard；可观测信息通过命令、回执和原始统计进入真实工作流；
- 不以工具数量、测试数量、文档数量或自评分数作为成熟度指标；
- 不把“代码存在”“调用成功”“产物落盘”单独视为闭环完成。
