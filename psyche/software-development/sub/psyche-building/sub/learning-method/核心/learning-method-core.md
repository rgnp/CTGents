## 一、认知姿态

1. **学透 = 能找出问题 + 能教给别人** — 只看懂它做了什么不算学透。能说出它的问题、边界情况、反直觉设计，**并且能用简单的话解释给不懂的人听**（Feynman Technique），才算学透。
2. **不带问题去读等于没读** — 打开一个项目前先问自己：我要从它身上学到什么？它什么地方可能有问题？
3. **代码本身是正文** — README、架构图、摘要都是索引。真正的内容在代码全文/论文正文里。
4. **从测试入手，从上到下** — 测试是代码的"可执行文档"。先读测试理解预期行为，再读实现验证理解。高层接口说明"做什么"，底层实现说明"怎么做"。

## 二、深度阅读检查清单

### 项目类

读源码全文（不只是目录结构和 README），按顺序过：

```
① 从测试入手
   - 先读单元测试/集成测试：理解每个模块的预期行为
   - 测试的名字告诉你"应该发生什么"
   - 带着"测试通过就是对的"去读实现

② 入口和包结构
   - 入口在哪？模块怎么划分的？
   - 每个模块的核心职责是什么？

③ 核心数据流
   - 核心循环/流程在哪？
   - 数据怎么流进来的？怎么出去的？
   - 关键的状态转换是什么？

④ 关键决策
   - 架构上最重要的几个选择是什么？
   - 留下了什么 trade-off？
   - 为什么这么设计而不是另一种方式？

⑤ 找问题（★ 学透的标志）
   - 边界情况没处理？（空值、异常、并发）
   - 静默数据丢失？（成功但不通知）
   - 用异常做控制流？
   - 安全漏洞？（路径穿越、输入校验）
   - 竞态条件？
   - 错误处理是否完备？

⑥ 对比与自检
   - 和我们系统的对应模块比，有什么差异？
   - 我们能从他身上学到什么？
   - 我们能不能避免他的错误？
```

### 论文类

```
① 读全文（不是只读摘要）
② 三问：
   - 解决了什么前人没解决的？
   - 隐藏假设是什么？
   - 留下了什么新问题？
③ 与已有 knowledge/ 交叉验证：支持/矛盾/补充
```

### 关口（学透的标准）

- **能教**：能用简单的话解释给不懂这个领域的人听。如果说不简单 → 没真懂（Feynman Technique）
- **能评价**：能说出它最好的地方是什么、它的问题是什么
- **反直觉发现**：至少找到一个自己之前不知道的认知冲击
- **关口检查**：如果只能说"它做了XXX"说不出"它有什么问题、也说不简单" → 读得不够深，继续找

## 三、避免认知过载

读复杂项目时，大脑的工作记忆有限（The Programmer's Brain, Felienne）：

```
识别过载信号：
  - 读了几遍还是不知道这段代码在干什么
  - 变量/函数名让你反复回去确认含义
  - 一个函数太长，读到后面忘了前面

应对策略：
  1. 分块（chunking）：把大模块拆成小块，每块理解透再往下
  2. 做标记（notation）：在关键决策点做笔记，不靠大脑记住
  3. 自上而下再自下而上：
     先了解高层模块划分（入口→依赖→数据流），
     再深入每个模块的细节实现，
     最后回到高层验证理解是否正确
  4. 停下来总结：每读完一个关键模块，用自己的话写一段总结
```

## 四、负面知识

- 只读 README/摘要就总结 = 知道了存在，没学会
- 只看架构图就下结论 = 细节全在代码里
- 只读一篇综述就说懂了 = 综述是索引，不是知识
- 读了不落盘 = 下一会话从头查
- 学了不找问题 = 只消费不批判，没真懂
