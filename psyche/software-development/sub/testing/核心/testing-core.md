## 一、定位

测试是软件开发的一个子领域。本 psyche 不重复父 psyche 中的通用工程原则，而是补充**测试特有的**质量判断、结构规范、反模式识别和优化策略。

父 psyche 的 9 条认知姿态和五筛子默认适用，以下只做扩展和特化。

## 二、子领域地图

```
测试质量的两轴评估:
                         好测试
                    ┌──────────┐
                    │   可信    │
                    │   · 测行为非实现  │
                    │   · 确定性    │
                    │   · 独立可重复  │
                    └──────────┘
    慢 ◄───────┬────────► 快
               │  有用    │
               │   · 抓真bug  │
               │   · 文档化行为 │
               │   · 重构安全网  │
               └──────────┘
                    坏测试
```

### 测试的五个层次

```
L0: 心态层 — 测试观（测行为 > 测实现 / 质量 > 覆盖率）
L1: 结构层 — AAA 模式 + 命名规范
L2: 工具层 — pytest 特性（fixture/parametrize/mock/conftest）
L3: 策略层 — 什么测、什么不测、风险导向
L4: 运维层 — 速度优化 + flaky 治理 + CI 集成
```

### 测试的价值排序

```
1. 抓 bug（回归检测）
2. 文档行为（可执行规范）
3. 重构安全网（敢改代码）
4. 驱动设计（TDD + 可测试性）
覆盖率是副产品，不是目标。
```

## 三、判断准则

### FIRST 原则（测试质量五维）

| 维度 | 含义 | 坏味道 |
|------|------|--------|
| **F**ast | 毫秒级运行，不依赖外部资源 | 测试里有 sleep、网络调用、文件 IO |
| **I**solated | 独立于其他测试，可任意顺序跑 | 测试依赖共享状态、依赖前一个测试的结果 |
| **R**epeatable | 任意环境结果一致 | 用了随机数/时间/网络而不 mock |
| **S**elf-validating | 自动通过/失败，不需人工解读 | 测试只打印结果不 assert，或 assert True |
| **T**imely | 在需要时及时写出，不积压 | 代码发布几个月后还没测试 |

### AAA 模式（测试结构三要素）

```
┌─────────────────────────────┐
│  Arrange（准备）             │
│  创建对象、设置输入、搭环境   │
├─────────────────────────────┤
│  Act（执行）                 │
│  调用被测方法，单一行代码      │
├─────────────────────────────┤
│  Assert（验证）              │
│  断言结果，单个逻辑概念        │
└─────────────────────────────┘
```

**铁律**：
- 三段间空行分隔
- Act 通常只有一行
- Assert 测一个逻辑概念（可多个 assert，只要测同一件事）

### 好测试 vs 坏测试

| 属性 | ✅ 好测试 | ❌ 坏测试 |
|------|---------|---------|
| 关注点 | 测行为（输入→输出） | 测实现（调了哪个方法/走了哪条路） |
| 确定性 | 每次结果一样 | flaky，有时过有时不过 |
| 耦合度 | 重构不碎 | 改实现就炸 |
| 可读性 | 名字说清场景+预期 | test_func1, test_a |
| 速度 | 毫秒级 | 秒级以上 |
| 失败定位 | 一眼知道哪里错 | 需要 debug 才知道 |
| 价值 | 抓真 bug | 满足覆盖率指标 |
| 维护 | 几乎不改 | 每次改代码都要跟着改 |

### 测什么、不测什么（风险导向）

| 代码类型 | 测试力度 | 理由 |
|---------|---------|------|
| 核心业务逻辑 | 🟢 全面覆盖 | 失败代价最高 |
| 基础设施/IO | 🟡 mock 外部依赖 | 测本层逻辑够用 |
| 配置代码 | 🔵 冒烟测试 | 验证能跑即可 |
| 简单 getter/setter | ⚪ 不测 | 测了没价值 |
| 第三方库调用 | 🟡 集成测试 | 不 mock，但只测关键路径 |

### pytest 最佳实践

**Fixture**：
- 用 `conftest.py` 共享 fixture，`scope="session"` 做一次性资源
- 内置 fixture（`tmp_path`/`monkeypatch`/`capsys`/`caplog`）优先于自造
- autouse=true 谨慎用——隐式依赖会让测试难理解

**Parametrize**：
- 同逻辑不同输入 → `@pytest.mark.parametrize`
- 用 `ids` 参数给用例可读的名字
- 每个参数组合是独立测试——失败不影响其他

**Mock**：
- **倾向用 stub 而不是 mock**（stub 返回固定值，mock 验证调用行为）
- mock 只用于外部边界（网络/文件/时间）
- 不要 mock 你不管有的东西
- 过度 mock = 测试测的是 mock 框架而不是你的代码

### 测试速度优化

```
定位慢测试 → 分类 → 针对性解决
   │               │
   ├─ pytest --durations=10  ├─ 不必要的集成 → mock
   │               ├─ 重复 setup → session-scope fixture
   │               ├─ 串行 → xdist 并行
   │               └─ 外部调用 → mock/回放
   │
   └─ 建立"慢测试预算"：CI 门禁卡超时
```

### 断言质量

| 坏断言 | 好断言 |
|--------|--------|
| `assert True` | `assert result == expected` |
| `assert len(list) > 0` | `assert list == [expected_item]` |
| 不写 assert（只打印） | 每个测试有明确断言 |
| 过于具体的 assert（耦合实现） | assert 外部行为 |

## 四、负面知识

- **过度 mock**：mock 了所有依赖 → 测试绿了但代码实际跑不通。mock 外部边界即可，内部依赖不需要 mock。
- **测试实现细节**：重构时测试比代码先碎 → 测试成了重构的阻力而不是助力。
- **把覆盖率当目标**：90% 覆盖率但断言什么都不验证 → 虚假安全感。无断言的覆盖比不覆盖更危险。
- **共享可变 fixture**：测试间共享状态 → flaky + 顺序依赖 → 最难调试的测试问题。
- **太长的测试**：一个测试测多个行为 → 失败时不知道哪里错。一个测试只测一件事。
- **sleep 等待**：异步操作用 sleep 等 → flaky 的万恶之源。用 `await` / 轮询 / 回调信号替代。
- **测试中的魔法数字**：`assert result == 42` 但不说明 42 是什么 → 用命名常量。
- **测试不读代码直接写**：对代码一知半解就写测试 → 测了错误的行为。先理解再测。

## 五、与父 psyche 的关系

| 父 psyche 原则 | 测试中的应用 |
|---------------|------------|
| 深层模块 > 浅层模块 | 测试应该测模块的外部行为（深层接口），不是内部实现 |
| 零容忍复杂度累积 | 坏测试要立刻修，不修会传染（破窗） |
| 代码给人读 | 测试是最重要的文档——名字要读得懂 |
| 没有测试的代码 = 遗留代码 | 这就是 Feathers 的原定义 |
| 曳光弹不原型 | 从最关键的行为先测，逐步加固 |
