## 一、认知姿态 — 审美设计的九个不动点

1. **美是有功能的，不是装饰** — 好审美让用户更快理解、更少犯错、更舒适地完成任务。设计不是为了"好看"，而是为了"好用且好看"。
   [→ knowledge/aesthetic-design/aesthetic-usability-effect.md]

2. **一致性产生美感，混乱产生疲劳** — 间距不一致、颜色不统一、字体混用——这些是界面"丑"的头号原因，不是因为配色不够潮。建立系统比追求惊艳更重要。Gestalt 的相似性原则为此提供了认知层面的解释——视觉相似=功能相似是人脑的默认推断。
   [→ knowledge/aesthetic-design/gestalt-principles-ui.md]

3. **用户不是设计师** — 你觉得好看的，用户可能看不懂。可读性 > 创意。交互的明确性 > 视觉的独特性。除非你做的是纯艺术项目。
   [→ Nielsen 10 Heuristics]

4. **内容即界面** — 内容的层次决定了设计的层次。先组织内容结构，再套视觉样式。反过来做 = 花架子。
   [→ Apple HIG / 排版原则]

5. **减法比加法难，但效果更好** — 每加一个颜色、一个装饰、一个动画，都要问：去掉它会损失什么？如果什么都不损失，就去掉。
   [→ Apple HIG "Deference" / Nielsen H8]

6. **交互的每个状态都要被设计，不是只有"正常状态"** — 空状态、加载中、错误、无网络、极限数据量——用户花在这些边缘状态上的时间比正常状态多得多。好看的截图谁都会做，好用的产品看边缘状态。
   [→ knowledge/aesthetic-design/interaction-patterns-deep.md]

7. **TUI 不是"在终端里假装 GUI"** — 等宽字体不是局限是特性（天然对齐），层次靠颜色/间距/缩进而非字号，border 是最强分组工具，box-drawing 字符替代圆角/阴影。用 TUI 的语法做 TUI 的设计，不要把网页设计思维硬塞进终端。同时，终端交互不是"回到 1999"——语义着色、进度反馈、渐进引导在现代 TUI 中都是必须的。
   [→ knowledge/aesthetic-design/tui-design-principles.md] [→ knowledge/aesthetic-design/cli-ux-patterns.md] [→ knowledge/aesthetic-design/textual-tui-patterns.md]

8. **好看 = 好用（Aesthetic-Usability Effect）** — Kurosu & Kashimura (1995) 发现：用户认为好看的东西更好用。好审美提升用户对产品的信任度和对微小问题的宽容度。这是设计杠杆，不是"用户肤浅"。但⚠️ 危险：好看可能掩盖可用性问题——测试时必须区分"感知易用性"和"实际易用性"。
   [→ knowledge/aesthetic-design/aesthetic-usability-effect.md]

9. **Gestalt 是自检工具，不是创作规则** — 接近/相似/闭合/连续/图底关系是描述人脑如何自动组织视觉信息，不是设计必须遵守的律令。用它们做自检（"用户看这个界面第一眼会把什么分到一组？"）比用它们做设计指导更有价值。不要为了"符合 Gestalt"而扭曲设计。
   [→ knowledge/aesthetic-design/gestalt-principles-ui.md]

## 二、设计判断框架

### A. 快速审美诊断（3-5-3 检查 + Gestalt 镜）

```
3秒扫描 → 第一眼看到的是最重要的内容吗？
5秒层次 → 视觉元素能清晰分出主次吗？
3个问题 → ①可读吗？②一致吗？③有什么可以去掉？

Gestalt 镜（闭眼过一遍）：
→ 哪些元素会被自动视为一组？（接近性/相似性）
→ 哪些元素会被自动补全？（闭合性）
→ 哪里图底关系混乱？（图底分离）
```

### B. 界面评价六维

| 维度 | 检查点 | 常见问题 |
|------|--------|---------|
| **排版** | 层次分明？行高合适？行长合理？ | 所有字一样大、行高太挤、字太多 |
| **配色** | 对比度达标？语义一致？不过度？6色体系有？ | 颜色太多、对比度不够、只靠颜色传信息、状态色无语义 |
| **布局** | 对齐一致？间距统一？留白够？ | 间距随意、内容填满所有空间、不对齐 |
| **交互** | 点击有反馈？状态可见？符合预期？边缘状态有设计？ | 按钮点击无反应、加载无指示、操作不可撤销、空状态空白页、错误状态只有错误码 |
| **一致性** | 同类元素同样式？同操作同交互？ | 同一功能不同位置不同样式、混搭风格 |
| **无障碍** | 色盲可区分？键盘可用？可放大？对比度达标？ | 红绿区分错误/成功、无法键盘导航、对比度 < 4.5:1 |

### B2. 交互场景检查清单

**表单设计：**
```
[ ] 标签在输入框上方（不是在框内当 placeholder）
[ ] 单列布局（不是多列混排）
[ ] 即时校验（不是在提交时才报错）
[ ] 错误提示具体可操作（不是"输入无效"）
[ ] 长表单分步（不是一屏 20 个字段）
```

**边缘状态（区分好产品与截图的区别）：**
```
[ ] 空状态有设计——首次使用有引导、搜索无结果有建议
[ ] 加载状态有指示——骨架屏 > loading 转圈
[ ] 错误状态有说明 + 用户能做什么
[ ] 极限数据量——标题溢出？列表太长？
[ ] 无网络——离线提示明确且有重试
```

**手势与反馈：**
```
[ ] 隐藏手势有视觉提示（滑动删除有文字暗示）
[ ] 破坏性操作有确认/可撤销
[ ] 点击/触摸反馈 < 100ms
[ ] 操作过程反馈（loading > 100ms 的操作）
```

### B3. TUI / CLI 设计检查清单（终端界面专用）

**配色体系（6 色系统）：**
```
[ ] 背景/表面/主色/强调色/文字/次要文字 6 色有体系关系（不是随手选）
[ ] 颜色总数 ≤ 6（不超时不疲劳）
[ ] 文字色用 85-90% 白，不用纯白 (#e6edf3 而非 #ffffff)
[ ] 状态色有语义（绿=正常/黄=繁忙/红=错误），不自创语义
[ ] 深色背景低饱和度，不刺眼
[ ] 对比度目标 5:1（比 WCAG AA 要求留余量）
[ ] 色盲友好——颜色不是唯一信息载体
```
[→ knowledge/aesthetic-design/color-semantics-accessibility.md]

**布局与分隔：**
```
[ ] 对话区无边框（内容区开放）
[ ] 输入框用上下边框与对话区隔开
[ ] 状态栏用上边框浮在底部（border-top）
[ ] 轮次间用 box-drawing 字符分隔 (╌╌╌ 而非 ···)
[ ] 间距一致（统一用 1-2 行空白做分组）
```

**消息渲染：**
```
[ ] 角色头+时间戳行内（"┃━ 你  ·  14:30"），不单独一行
[ ] 消息正文缩进 2 格（与角色头对齐）
[ ] 左粗条区分归属（橙=用户，蓝=agent）
[ ] 一轮内只挂一次角色头（工具/思考阶段不重复出）
[ ] 折叠区（思考/工具）透明背景，与对话区融合
[ ] 不模拟 GUI 气泡（终端没有真正的气泡效果）
```

**信息层次：**
```
[ ] 重要信息用 color + bold 突出
[ ] 次要信息用 dim 淡化（时间戳、状态细节）
[ ] 辅助信息用 semary 色降级
[ ] 每屏不超过 4 种颜色同时出现
[ ] border 厚度统一用 thin（不用 heavy）
```

**CLI UX 模式（非持久化 TUI 专用）：**
```
[ ] 耗时 > 100ms 的操作有 spinner 指示
[ ] 耗时 > 3s 的操作有进度条 + 当前步骤说明
[ ] 错误消息结构：什么错了 → 为什么 → 用户能做什么
[ ] 首次运行/无配置时显示"如何开始"的三个示例，不是完整 help
[ ] --help 默认折叠，只展示最常用的 20%，完整参数用 --help-all
[ ] 支持多输出格式：默认人类可读 + --json 机器可读 + --quiet 脚本友好
[ ] 命令名一致（动词-名词结构，不用同义词混搭）
[ ] 不用纯文本吐所有信息——表格/分组/标题辅助扫描
```
[→ knowledge/aesthetic-design/cli-ux-patterns.md]

**Textual TUI 框架实践（持久化 TUI 专用）：**
```
[ ] 先画草图再写代码（终端矩形分区图）
[ ] 用 fr（分数单位）做响应式布局，固定元素用 dock
[ ] 可滚动内容用 VerticalScroll（不用 Vertical）
[ ] 大量数据用 ListView（虚拟滚动），不循环生成 widget
[ ] 静态内容只在初始化时设置，不频繁更新
[ ] 定时刷新用 set_interval，不用自定义 loop
[ ] 用 reactive 属性而非手动 refresh
[ ] 交互必须有键盘替代方案（终端光标不是鼠标）
[ ] 颜色方案兼容 256 色 + TrueColor 回退
```
[→ knowledge/aesthetic-design/textual-tui-patterns.md]

### C. 风格选择指南 [L3 — 基于实践推理，未经过用户研究验证]

| 产品定位 | 推荐风格 | 理由 |
|---------|---------|------|
| 企业级/B2B | 扁平/Material | 效率优先，减少视觉干扰 |
| 内容型（新闻/阅读） | 扁平 + 好排版 | 内容本身是明星 |
| 创意/个人品牌 | Brutalist/Glassmorphism | 个性=品牌差异化 |
| 工具类（健康/音乐） | Neumorphism/简约 | 手感+沉浸感 |
| 金融/医疗 | 保守扁平 + Material | 信任感 > 个性化 |
| TUI 工具 | 深色 + 语义色 + 等宽排版 | 终端视觉语法，不模拟网页 |

## 三、负面知识

- **不要用"我感觉"替代设计系统** — "我觉得紫色和蓝色配"但没有任何设计依据 → 下一个开发者接手时只能猜你的意图
- **不要为了"潮"牺牲可用性** — Neumorphism 在 2020 年火但可识别性差（用户不知道按钮能不能点），Brutalism 在创意圈火但企业产品用 = 自杀
- **不要在深色模式使用纯黑背景 (#000000)** — 纯黑在 OLED 上会产生光晕，且和浅色文字对比过于强烈导致阅读疲劳。用深灰 (#121212)
- **不要使用纯色文字在纯色背景上** — 即使对比度达标也缺乏层次感。文字带微妙的透明度（如 #000000 87%/60%/38%）比纯色更有质感
- **不要在布局上"感觉对齐"** — 不对齐是界面脏乱的头号原因。用网格系统，间距统一用 4/8/12/16 的倍数
- **不要用动效填充空白** — 用户操作后页面在加载，你用了一个旋转动画 → 用户还是不觉得快。动效不能替代性能优化
- **不要只设计"完美状态"** — 截图上只展示正常数据、完美布局。用户实际看到的是空状态、加载中、错误提示、极限数据。这些边缘状态没设计 = 产品上线后大部分时间用户看到的都是你没设计过的页面
- **不要让表单超过用户耐心** — 10+ 字段不分步、没有默认值、标签放在框内（填了内容就看不清标签了）、提交才报错——这些是用户放弃填表单的头号原因
- **不要隐藏关键导航** — 汉堡菜单（hamburger menu）只有在内容实在放不下时才用。用户能找到的导航才是好导航，藏起来的导航等于没有导航
- **不要自创手势** — 平台有自己的手势惯例（iOS左滑删除、下拉刷新）。用户已经学会了，你自创一个"下滑删除，上滑编辑"只会让用户困惑
- **不要把 Gestalt 当科学律令** — Wikipedia 指出 Gestalt 原则缺乏强定量研究支撑。它们是设计启发，不是真理。用在自检上比用在创作上更有价值。[→ knowledge/aesthetic-design/gestalt-principles-ui.md]
- **不要依赖审美掩盖功能缺陷** — Aesthetic-Usability Effect 的暗面：好看的界面在测试中可能隐藏可用性问题。测试时必须区分"感知易用性"和"实际易用性"。[→ knowledge/aesthetic-design/aesthetic-usability-effect.md]
- **不要只在正常状态下测试** — 测试时用"剥离审美"的版本对比：如果去掉所有颜色/间距/装饰，用户操作路径还通吗？通→设计是附加价值。不通→设计在掩饰结构问题。[→ knowledge/aesthetic-design/aesthetic-usability-effect.md]
- **不要在 TUI 里模拟 GUI 元素** — border-radius、气泡、阴影在终端不存在。用 box-drawing 字符和 border 做分组，不要试图"让终端看起来像网页"。[→ knowledge/aesthetic-design/tui-design-principles.md]
- **不要用超过 6 种颜色** — 终端等宽字体的视觉负担比 GUI 大，颜色越多眼睛越累。6 色足够区分所有信息层次。[→ knowledge/aesthetic-design/tui-design-principles.md]
- **不要盲目加装饰** — 每个 border、每个字符、每个颜色都要问：没有它会丢失什么信息？丢失了就不能删，不丢失就去掉。[→ knowledge/aesthetic-design/tui-design-principles.md]
- **不要在 TUI 里用纯黑背景 (#000000)** — 在 OLED 屏幕上有光晕，在 LCD 上显得脏。用深灰 (#1a1a2e 或 #0d1117)。[→ knowledge/aesthetic-design/color-semantics-accessibility.md]
- **CLI 不要只输出错误码** — 错误消息结构：什么错了 → 为什么 → 用户能做什么。扔个退出码让人去查文档 = 你在逼用户离开你的工具。[→ knowledge/aesthetic-design/cli-ux-patterns.md]
- **CLI 不要不输出进度** — 耗时 > 100ms 没反馈 = 用户以为程序卡死了。spinner / progress bar / 剩余时间，选一个。[→ knowledge/aesthetic-design/cli-ux-patterns.md]

## 四、核心矛盾

| 矛盾 | 说明 | 处理原则 |
|------|------|---------|
| 标准化 vs 个性化 | 一致性要求遵循规范，但所有产品看起来都一样 | 基础层标准化（间距/排版/色彩系统），品牌层个性化（配色/动效/插画风格） |
| 极简 vs 表现力 | 太多内容全去掉只剩文字 vs 太多装饰什么都看不清 | 80% 极简 + 20% 表现力——功能优先，在关键触点上做文章 |
| 新颖 vs 可预期 | 用户喜欢新事物但讨厌不可预测 | 创新在体验的"惊喜时刻"（空状态动画/微交互），核心流程保持平台惯例 |
| 感知美 vs 真实用 | 好看的东西被认为更好用，但也可能掩盖真实缺陷 | 设计时用好审美杠杆，测试时剥离审美检查功能完整性 |
