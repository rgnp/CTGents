> 构建日期: 2026-06-21 | 状态: 初版
> 基于: 业界工程能力矩阵/经典书籍/前沿实践调研

## 一、软件开发知识拓扑

```
软件开发能力
│
├── 代码层（微观）
│   ├── 命名（意图清晰、一致性）
│   ├── 函数（小、单一职责、无副作用）
│   ├── 注释（解释为什么，不解释是什么）
│   ├── 控制流（早返回、避免深层嵌套）
│   └── 错误处理（不吞异常、有意义的错误信息）
│
├── 设计层（中观）
│   ├── 面向对象设计（SOLID）
│   ├── 设计模式（GoF 23）
│   ├── 函数式编程概念（不可变、纯函数）
│   └── 接口设计（最小暴露、稳定契约）
│
├── 架构层（宏观）
│   ├── 模块划分（高内聚低耦合）
│   ├── 分层架构（Clean Architecture / 洋葱架构）
│   ├── 依赖方向（上层依赖抽象、不依赖具体实现）
│   └── 项目结构（src布局、设置管理、包组织）
│
├── 质量层
│   ├── 测试（单元/集成/E2E/契约测试）
│   ├── 代码审查（Google eng-practices）
│   ├── 静态分析（lint/type check）
│   └── CI/CD（自动化门禁）
│
├── 演进层
│   ├── 重构（安全步骤、识别坏味道）
│   ├── 技术债务（记录、排期、偿还）
│   └── 版本化演进（渐进式、不一次性大改）
│
└── 判断层（贯穿所有层）
    ├── 权衡分析（列出选项→评估→记录理由）
    ├── 上下文感知（没有普适方案、只有适用方案）
    └── 成本意识（实现成本/维护成本/学习成本）
```

## 二、测试金字塔（2026版）

```
         /\
        /E2E\          ← 少量：关键用户流程
       /------\
      / 集成   \       ← 适量：模块间交互、外部依赖
     /----------\
    /  单元测试   \    ← 大量：单函数/单类的行为验证
   /--------------\
  / diff coverage  \   ← 新代码80-90%覆盖
 /------------------\
```

关键点：不是"越多越好"，而是"每个层级放对类型的测试"。E2E测试慢、脆弱、难维护 → 只放最关键的用户流程。单元测试快、稳定、好定位 → 主力。

## 三、代码坏味道速查表（需要重构的信号）

| 坏味道 | 问题 | 常用重构手法 |
|--------|------|-------------|
| 过长函数 | 做了多件事 | Extract Method |
| 过长参数列表 | 依赖太多 | Introduce Parameter Object |
| 重复代码 | 违反DRY | Extract Method → Pull Up |
| 过大类 | 职责过多 | Extract Class |
| 散弹式修改 | 改一处要改多处 | Move Method/Field |
| 依恋情结 | 一个方法过度依赖另一个类 | Move Method |
| 数据泥团 | 多个数据项总是一起出现 | Extract Class |
| 基本类型偏执 | 用基本类型表示领域概念 | Replace Primitive with Object |
| switch语句 | 类型分支过多 | Replace with Strategy/Polymorphism |
| 临时字段 | 对象中有只偶尔使用的字段 | Extract Class |

## 四、核心张力

| 张力 | 一方 | 另一方 | 判断 |
|------|------|--------|------|
| 写快 vs 写好 | 快速交付、快速验证 | 代码质量、长期可维护 | 短期可以但必须记债 + 排期还 |
| 抽象 vs 简单 | 抽象可扩展、解耦 | 简单易理解、低成本 | 只在抽象解决真实问题时才加 |
| 测试覆盖率 vs 测试质量 | 高覆盖=高信心 | 有价值的断言比数字重要 | 80%线+diff coverage，关注assertion质量 |
| 重构 vs 重写 | 有序改进，低风险 | 彻底换掉，不背历史包袱 | 能重构就别重写，重写代价被低估 |
| 通用 vs 专用 | 模式通用、复用性高 | 专用简单、不引入抽象 | 三个用例再抽象（rule of three） |

## 五、单人开发 vs 团队开发的差异

| 维度 | 单人 | 团队 |
|------|------|------|
| 代码标准 | 自己看得懂即可 | 全员一致、可被他人review |
| 测试 | 关键路径 | 每个PR都测 |
| 文档 | 最少必要 | 显式知识传递 |
| 架构 | 怎么方便怎么来 | 模块边界清晰、降低耦合 |
| 技术债务 | 可以容忍 | 需系统管理 |

这个psyche采用团队标准作为自己的标准（因为目标是"资深软件工程师"），但考虑到单人开发的实际情况，在深度和严格度上可调整。
