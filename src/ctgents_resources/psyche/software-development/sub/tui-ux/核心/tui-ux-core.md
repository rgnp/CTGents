## 一、认知姿态 — 四个不动点

### 1. 好的 TUI = 用户永远知道三件事
扫一眼就能回答：**现在是什么状态？** **我能做什么？** **刚才发生了什么？**
状态栏回答第一问，placeholder/快捷键回答第二问，transcript 回答第三问。
三问有一个答不上来 → UX 有缺口。
[→ interaction-constraints + status-feedback]

### 2. 中断优于不可中断，可恢复优于中断后重来
长操作（LLM 回答、代码执行）必须能被中断。中断后的状态必须清晰：现场没丢、用户可以调整后继续、也可以完全终止。
用户中断不是因为"不想看结果"——往往是想调一下方向。中断+恢复 = 对话的转向杆。
[→ interrupt-resume]

### 3. 不丢数据 > 一切
用户的输入、会话、状态都是资产。_busy 期间不清空输入框、崩溃后自动保存——交互设计要把"防丢失"放在"防误操作"之前。
[→ interaction-constraints + interrupt-resume]

### 4. 功能可发现 > 功能多
一个功能如果用户不知道它存在，等于没有。但 footer 空间有限——用分层发现：
- 核心操作（中断/提交）→ footer 可见
- 常用操作（历史/清屏）→ show=False 绑键 + /help 文档
- 高级操作（诊断/管理）→ 仅命令系统
[→ keyboard-design + command-system]

## 二、质量判断准则

### 准则 1: 三问测试
不看代码，打开 TUI 截图。秒答：现在什么状态？我能做什么？刚才说了什么？
→ 全部秒答 = UX 过关。有一个需要猜 = 要修。

### 准则 2: 状态迁移图有无断裂
画出所有状态和状态之间的迁移（空闲/运行中/中断中/已中断/错误）。每个状态：
- 用户能感知当前状态吗？
- 状态迁移有视觉反馈吗？
- 有"回不去"的绝路吗？

### 准则 3: 键盘可完成所有核心操作
不用鼠标（或终端无鼠标支持时），所有核心操作可完成吗？
→ 发送、中断、恢复、退出、选存档、翻历史 — 全键盘可操作。

### 准则 4: 慢操作有即时反馈
提交消息 → 状态栏立即变 `● 思考中`（不是等第一个 token）。
工具调用 → Collapsible 里实时追加条目（不是全部完成才显示）。
Ctrl+C 等重操作 → 响应 < 200ms。

### 准则 5: 信息同源不重复
token 用量在状态栏还是消息区？只在一处。
如果有两处显示同一信息 → 冗余噪音，删一个。

### 准则 6: 危险操作有护栏
删除会话 → 两步确认（d → "⚠️ 确认删除？再按 d 确认"）。
退出程序 → Ctrl+Q（不易误触），不是常见的 Ctrl+C。
_clear 清上下文 → 命令触发（/clear），不可逆转但有提示。

### 准则 7: 帮助可发现
新用户进来能不能知道：
- 有命令系统（/help → 指令列表）
- 有快捷键（footer 展示最核心的 2 个 + placeholder 提到 /help）
- 有功能（placeholder 的变化引导）

## 三、负面知识 — TUI UX 常见错误

### 错误 1: 静默失败
操作无效但不告诉用户为什么。"发送"键按了没反应 → 用户以为崩了。
→ 必须有反馈：_busy 时按 Enter 虽然被吞，但状态栏写着"思考中"，用户知道为什么。

### 错误 2: 模态 trapped
弹出一个不可取消的对话框/状态 → 用户按任何键都没反应。
→ 每个模态状态必须有退出路径（Esc = 万能取消）。

### 错误 3: 默认值不显示
切换模型/切换会话后不显示当前选择 → 用户不知道现在用的是什么。
→ 状态栏显示当前模型+会话名。

### 错误 4: 快捷键冲突
Ctrl+C 在终端里既是"复制"又是"退出" → 用户永远复制不了或永远退不出。
→ 不要让一个键承担两个不可调和的功能。让 Ctrl+C=复制，Ctrl+Q=退出。

### 错误 5: 长操作无进度
LLM 回答启动后 2 秒没有 token → 用户不知道是卡了还是在思考。
→ 状态栏即时反馈 + 思考内容流式展开。

### 错误 6: 历史丢失
会话列表不显示、换了会话前一个消失、崩溃丢输入 → 用户资产丢失。
→ 自动保存、显式会话列表、_busy 期间不清输入框。

### 错误 7: 帮助信息罗列无分层
`/help` 把 16 个命令全部列出等长 → 用户找不到重点。
→ 帮助应分层：核心命令优先 + 高级命令折叠/后置。

## 四、核心矛盾

| 矛盾 | 说明 | 处理原则 |
|------|------|---------|
| 信息密度 vs 简洁 | 状态栏一行塞多少？ | 只放"做决策需要"的数据；用分隔符组织；余下放 /help |
| 安全护栏 vs 流畅 | 确认删除 vs 一键完成 | 两步确认仅用于不可逆操作；日常操作不加护栏 |
| 新手引导 vs 老手无扰 | 提示太多烦、太少懵 | 分层：footer(核心2个) → placeholder → /help → 命令列表 |
| 可发现 vs footer空间 | 16 个命令、6 个快捷键、footer 一行 | show=True 只给最核心 2 个，其余 show=False + /help |
| 状态栏实时 vs 性能 | 0.5s 刷新频率 vs 渲染开销 | 缓存比较（status_cache），内容不变就不重渲染 |

## 五、自检清单

```
[ ] 三问测试：状态？能做什么？刚才说了什么？
[ ] 所有状态有迁移路径，无绝路？
[ ] 键盘可完成所有核心操作？
[ ] 慢操作(>100ms)有即时反馈？
[ ] 同一信息只出现一次？
[ ] 删除/退出有确认？
[ ] /help 可发现，分层展示？
[ ] 运行中提交被吞有解释（不是静默）？
[ ] 中断后可恢复，现场不丢？
[ ] 快捷键无冲突（Ctrl+C 不绑 quit）？
```
