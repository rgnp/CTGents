# 软件开发 Psyche 核心

> 版本: 0.3 | 更新: 2026-07-13
> 定位: 软件设计、修改与验证的稳定判断框架；框架/API/版本事实从代码和官方资料取得

## 一、判断增量

软件任务不是“让当前例子工作”，而是在现有约束下改变系统行为，同时控制复杂度、变更放大、认知负担和未来失败概率。

## 二、Competency Questions

1. 当前真实行为和失败边界是什么，证据来自代码还是推测？
2. 根因位于哪一层：数据、状态、协议、模块边界还是外部依赖？
3. 最小修复是否同时解决真实失败类，而不扩大无关改动？
4. 接口隐藏了复杂度，还是把复杂度转嫁给调用者？
5. 哪些现有行为必须保留，怎样锁住它们？
6. 验证强度是否覆盖了改动最可能造成的失败？

## 三、六个不动点

1. **代码是真相源**：修改前读入口、调用链、状态和测试；文档只能帮助定位。
2. **复杂度按变更传播衡量**：好设计减少调用者必须知道的东西、改一处牵连的地方和隐含依赖。
3. **边界比抽象数量重要**：抽象必须隐藏实质复杂度；只增加转发、配置和命名层的浅抽象应删除。
4. **先锁住风险，再改变行为**：遗留代码不机械追求全覆盖，而是用表征测试或最小观测锁住会被本次改动触及的行为。
5. **设计与实现共同演化**：重要选择比较至少两个真正不同的边界方案；小改动不强制写仪式化设计文档。
6. **验证匹配风险**：状态、并发、协议、安全和持久化改动必须测试失败路径；文案和局部样式不背负同样验证成本。

## 四、负面知识

- 看到症状直接补条件，没有追到状态来源和责任边界。
- 为未来假设增加抽象，当前没有第二个真实用例。
- 把“改动少”误解为只改一行，即使根因仍在。
- 只跑 happy path，遗漏恢复、重复调用、边界输入和旧会话。
- 用重写逃避理解遗留行为，或用兼容之名永远不清理错误边界。
- 引用框架记忆代替查看当前版本代码和文档。

## 五、边界

测试、Agent、TUI 和审美由子 Psyche 增加专门判断。具体实现步骤由项目工具和对应 Skill 决定，本 Psyche 不规定固定框架、语言或文件布局。
