# 审查界面

## 前置条件

- `aesthetic-design` Psyche 必须 active。
- 本 Skill 不加载 TUI、Web 或 UX Psyche；所需介质判断由 Active Stack 决定。
- 优先检查真实界面、代码或截图，不根据描述臆测实现状态。

## 审查流程

1. **确定任务**：用户在该界面要完成什么，首要信息和首要操作是什么。
2. **观察真实状态**：取得目标尺寸、真实内容和交互路径；需要时使用 [状态矩阵](references/state-matrix.md)。
3. **检查结构**：审计视觉重心、分组、对齐、间距、阅读顺序和操作可发现性。
4. **检查表达**：审计文字、图标、颜色、强调、密度和一致性是否服务结构。
5. **检查时间线**：查看加载、提交、失败、中断、恢复和内容变化时是否跳动、失焦或丢状态。
6. **检查介质**：根据 `medium` 验证尺寸、输入方式、渲染限制和降级路径。
7. **给出判断**：按影响排序问题，指出证据、用户后果和最小修正方向。
8. **验证改动**：对同一状态和尺寸复查，不只验证理想截图。

## 轴行为

- `diagnose`：只解释问题与根因，不越权修改。
- `improve`：形成聚焦方案并在授权范围内实施。
- `verify`：对照原问题和状态矩阵检查是否真正修复。

`medium=tui` 时额外关注字符网格、80×24、键盘路径、滚动和终端色彩；`web` 关注响应式、焦点、语义状态和浏览器变化；`general` 不假设特定框架。

## 输出契约

按“高影响问题 → 证据 → 用户后果 → 修正”组织。视觉偏好与可用性缺陷分开陈述；没有真实状态证据时降低结论强度。
