# 逐行精读模式

> 轴: depth=deep | 触发: 用户说"精读"/"deep read"/"逐行分析"或对候选方法做最终评估

---

## 操作准则

**目标**：对论文做接近审稿人级别的全面审计。不仅理解"它做了什么"，还要判断"它做对了吗"。

## Normal 基础上的追加

在完整 P0→P5 流程的基础上，追加以下深度检查：

### D1 · Warrant 逐条审计

对 P1 中识别出的每个 warrant，逐一检查：

1. 这个 warrant 的 backing 是否被论文自己验证？
   - 例：warrant 是"因为 multi-head attention 能捕获多尺度特征"
   - 检查：论文有没有可视化/量化证明 attention 确实捕获了多尺度？
   - 如果没有 → 这是 unvalidated backing

2. 这个 warrant 的隐含前提是什么？前提是否成立？
   - 例：warrant 是"因为我们的模块是即插即用的"
   - 隐含前提：模块不依赖特定 backbone 设计
   - 检查：是否在多个 backbone 上验证过？

3. 不同 warrant 之间是否有冲突？
   - 例：W1 声称模块轻量，W2 声称模块充分表达——两者矛盾吗？

### D2 · 实验设计审计

1. **消融实验完整性**
   - 每个声称贡献的组件都有消融吗？
   - 缺消融的组件标出来

2. **误差分析**
   - 论文报了 error bar 吗？几次重复？
   - 如果没有——标"不可复现风险"

3. **算力/效率报告**
   - 有没有报参数量、FLOPs、推理时间？
   - 如果没有——标"部署可行性未知"

### D3 · 引用追溯

1. 论文的核心技术组件追溯到原始出处
2. 检查"新方法"和新 baseline 的时间线——有没有"比旧方法新"的嫌疑？
3. 论文声称解决的"前人问题"是否有实际引用支撑？还是稻草人？

### D4 · 脆弱点分析

输出时追加一节"脆弱点"：

```markdown
## 脆弱点
- [条件C1下] 结论在 X 条件下可能不成立，因为 Y
- [假设H1] 假设 A 在实际部署中可能不成立
- [gap] 缺少对 Z 的验证
```

## 输出增强

- P5 卡片追加 warrant 审计、实验审计、引用追溯、脆弱点四节
- 如果需要，追加"如果我是审稿人会问的问题"（3-5 个）

## 时间预算

不设上限。一篇论文的 deep read 可能需要 2-4 小时。
