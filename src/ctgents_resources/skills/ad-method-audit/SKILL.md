# AD Method Audit — 自动驾驶方法审计

> 对任何自动驾驶方法，逐条过六不动点。不总结论文，不评估贡献——只审计方法在闭环中的真实位置。
> 来源：psyche/autonomous-driving/核心/autonomous-driving-core.md §三

---

## 触发时机

- 读 AD 论文的方法章节后
- 用户问"这个方法靠谱吗""这个设计合理吗"
- 作为 paper-deep-read / paper-walkthrough / co-read 的补充审计层

---

## 六维审计

每维输出：✅ 通过 / ⚠️ 有隐忧 / ❌ 不通过 / ❓ 信息不足

### 1. 闭环层级定位

**问题**：方法位于感知/预测/规划/控制的哪一层？依赖哪些上游假设？上游误差会怎么传播？

**检查**：
- 是否假设上游完美（GT 感知、GT 检测、128m 完美范围）？
- 上游输出如果有 10% 噪声/延迟/丢失，下游会怎么退化？论文讨论了吗？

### 2. 物理与时序一致性

**问题**：方法是否保持几何、运动学、时序和交互一致性？

**检查**：
- 预测的轨迹是否满足车辆动力学约束（最大转角、加速度限制）？
- 多帧预测之间是否时序平滑？（自回归建模 vs 独立预测）
- 交互建模：ego 和其他 agent 的状态演化是否因果闭环？（ego 动了 → 其他 agent 怎么反应？）
- 如果有视觉输入：是否保持了 3D 几何一致性？

### 3. 开环→闭环 warrant

**问题**：离线指标的提升通过什么机制改变规划/安全/舒适性？

**检查**：
- 如果离线 minADE 降低 5%，闭环会有什么可观测的行为变化？论文解释了吗？
- 开环指标选型是否匹配闭环需求？（比如 minFDE 对规划无用、碰撞率才有用）
- 是否做了任何闭环/半闭环验证？

### 4. 长尾与失败模式

**问题**：平均指标之下，失败模式被掩盖了吗？

**检查**：
- 报告了哪些指标？只有均值还是有分布/分位数/最坏情况？
- 场景覆盖：论文测试了哪些场景类型？缺了哪种（夜间/雨雪/拥堵/路口/切入）？
- 有没有 failure case 分析？

### 5. 资源约束

**问题**：延迟、算力、数据预算是否现实可行？

**检查**：
- 推理延迟是否满足实时要求（≥10Hz 或论文声明目标频率）？
- 训练资源是否可复现（GPU 卡数、训练时长）？
- 是否需要特殊硬件（Orin、自定义芯片）？
- 是否依赖离线预处理或未来帧信息（teacher forcing 泄露）？

### 6. 证据时效与路线判断

**问题**：论文的 baseline、数据集和结论是基于哪个时间点的认知？

**检查**：
- **需要查询当前 knowledge/ 确认**——不使用 Psyche 记忆的固定结论
- 与同期方法比较是否公平？（同一数据集、同一协议）
- 论文的贡献在 2026 年是否仍成立，还是已被后续工作覆盖？

## 输出格式

```markdown
## AD 审计：[论文简称]

| 维度 | 判定 | 关键发现 |
|------|------|---------|
| 闭环层级 | ✅/⚠️/❌/❓ | 一句话 |
| 物理时序一致性 | ... | ... |
| 开环→闭环 warrant | ... | ... |
| 长尾与失败 | ... | ... |
| 资源约束 | ... | ... |
| 证据时效 | ... | ... |

**最危险的假设**：[当 X 不成立时，整个方法最可能在哪一步崩溃？]
**闭环可用性**：[如果把这个模块放进真实 planning stack，需要补什么？]
```

---

## 边界

- 不替代 paper-deep-read 的论证审计——ad-method-audit 是领域特化的补充层
- 证据时效维度必须查询 knowledge/ 当前状态，不凭记忆
- 信息不足时标 ❓，不硬填
